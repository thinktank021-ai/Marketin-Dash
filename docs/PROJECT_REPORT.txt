1. خلاصه مدیریتی
======================================================================

این پروژه یک داشبورد مدیریتی بازاریابی برای «دفتر دنیاگردی» است که اطلاعات
بازاریابی، لیدها، قراردادها، مسیرها، هزینه‌ها، Google Ads، Search Console و
گزارش Telegram را در یک محیط فارسی، راست‌چین، واکنش‌گرا و داده‌محور جمع می‌کند.

پروژه با React 19، Vinext/Next App Router، Vite، Cloudflare Workers، Cloudflare
D1، Drizzle ORM و Cloudflare Sites ساخته شده است. Google Sheets منبع اصلی داده‌های
ورودی و تماس است. Google Ads و Search Console به‌صورت اختیاری و مستقل برای هر
برند/دفتر متصل می‌شوند. اعتبارنامه‌ها در D1 ذخیره می‌شوند اما قبل از ذخیره‌سازی
با AES-GCM رمزنگاری می‌شوند.

اصل مهم محصول این است که داشبورد نباید با داده ناقص یا اتصال قطع‌شده، عدد صفر
ساختگی نشان دهد. در صورت قطع منبع، آخرین داده معتبر حفظ می‌شود و وضعیت اتصال
واقعی و هشدار آن به مدیر نمایش داده می‌شود.

قابلیت‌های اصلی فعلی:

- داشبورد اصلی تماس‌ها، لیدها، قراردادها، مسیرها، کانال‌ها و کارشناسان.
- گزارش بازه زمانی با تقویم شمسی و انتخاب بازه شروع/پایان.
- تنظیمات چند دفتر/برند با جداسازی داده و منابع.
- Google Sheets با کش، کشف ماه‌ها و کنترل سلامت داده.
- Google Ads با گزارش کمپین، هزینه، کلیک، لید، CPL، CAC و هشدارها.
- Search Console با KPI، نمودار، جدول، مقایسه، سورت، فیلتر، صفحه‌بندی و CSV.
- مرکز اقدام SEO، صف اقدام، Opportunity Radar و دسته‌بندی محتوا/لینک‌سازی.
- استخراج شماره تماس با فیلترهای مدیریتی و خروجی CSV.
- مدیریت قراردادهای ردیفی و قراردادهای تجمیعی قبلی.
- Telegram Bot با کاربران مجاز، گزارش دستی، خودکار، پایان روز و هشدار تغییر.
- PWA، Service Worker، کش آخرین داده و وضعیت آفلاین.
- ورود مدیریتی با نشست ۲۰ دقیقه‌ای، scrypt، کوکی امن و محدودیت تلاش.
- مرکز سلامت داده و ابزار backup/diagnostic امن بدون افشای PII و Secret.

4. تصمیم‌ها و الزامات ثبت‌شده در Personal Context
======================================================================

این بخش خلاصه‌ای از تصمیم‌ها و ترجیحات پروژه است که در گفتگوهای قبلی ثبت شده
و باید در تغییرات بعدی رعایت شود.

4.1. صحت داده و شمارش

- تنها وقتی یک ردیف لید واقعی شمرده می‌شود که ستون «منبع فایل» پر باشد.
- ناقص بودن سایر فیلدها مانع شمارش ردیف معتبر نمی‌شود.
- ردیف دارای منبع اما فاقد مسیر باید با عنوان «مسیر ثبت نشده» نشان داده شود.
- ردیف دارای منبع اما فاقد کارشناس باید «کارشناس ثبت نشده» باشد.
- دسته مبهم «سایر» نباید بدون تصمیم مدیریتی ساخته شود.
- مسیرهای تفلیس، باتومی و گرجستان در داشبورد با عنوان گرجستان ادغام می‌شوند.
- تبلیغات گوگل با عنوان گوگل ادز نمایش داده می‌شود.
- آژانسی مستقل است.
- اختلاف کل با تفکیک کانال/مسیر/کارشناس باید در مرکز سلامت داده دیده شود.

4.2. تاریخ و بازه

- تقویم شمسی باید کامل و ۷ ستونه باشد.
- روزهای ماه نباید حذف شوند.
- انتخاب بازه با شروع و سپس پایان انجام می‌شود.
- روز آینده قابل انتخاب نیست.
- بازه می‌تواند چند شیت ماهانه را پوشش دهد.
- بازه پیش‌فرض گزارش از ابتدای ماه تا آخرین روز کامل موجود است.
- روز جاری Search Console به‌دلیل نهایی نبودن داده گزارش نمی‌شود.

4.3. منابع و اتصال

- Google Sheets برای هر برند مستقل است.
- Google Ads برای هر برند Service Account مستقل دارد.
- Search Console اختیاری و برای هر دفتر مستقل است.
- قطع اتصال نباید باعث صفر شدن داشبورد شود.
- آخرین داده معتبر باید با هشدار stale نگه داشته شود.
- بروزرسانی دستی باید منابع قابل مشاهده را دوباره درخواست کند.

4.4. مالی

- CPL = هزینه کانال تقسیم بر لید معتبر همان کانال.
- CAC = هزینه کانال تقسیم بر قرارداد قابل انتساب همان کانال.
- مقدار ناشناخته نباید به‌صورت صفر نمایش داده شود.
- صفر صریح با «هزینه ثبت نشده» متفاوت است.
- Google Ads از API خوانده می‌شود و با نرخ TRY به تومان تبدیل می‌شود.
- کانال‌های بدون هزینه وارد محاسبه CPL/CAC نمی‌شوند.
- هزینه Google Ads/واتساپ/فرم سایت از نظر مالی یک گروه انتسابی دارند اما
  تعداد خام آن‌ها در کارت‌های جدا قابل نمایش است.

4.5. امنیت

- اعتبارنامه‌های Service Account نباید در UI عمومی برگردند.
- Private Key و Developer Token باید رمزنگاری‌شده ذخیره شوند.
- گزارش تشخیصی نباید PII، Secret یا Credential خام داشته باشد.
- ورود مدیریتی نشست ۲۰ دقیقه‌ای دارد.
- فعالیت واقعی کاربر نشست را تمدید می‌کند.
- APIهای اصلی بدون نشست معتبر پاسخ مدیریتی نمی‌دهند.

4.6. SEO و Search Console

- Search Console فقط خواندنی است.
- کاربر می‌تواند تا چهار KPI اصلی را انتخاب/مقایسه کند.
- نمودارها روی hover مقدار هر نقطه را نشان می‌دهند.
- جدول Search Console ستون‌های قابل سورت دارد.
- Opportunity Radar باید قابل کلیک و فیلتر باشد.
- کارت‌های KPI باید با کلیک جدول پایین را فیلتر کنند.
- فرصت‌ها باید به «بهینه‌سازی محتوا» یا «محتوا + لینک‌سازی داخلی» وصل شوند.
- منطق فرصت‌یابی باید نسبت به حجم داده هر Search Console پویا باشد.


======================================================================
5. معماری کلان سیستم
======================================================================

جریان کلی درخواست:

مرورگر
  -> صفحه React/Vinext
  -> Cloudflare Worker
  -> guardAppRequest و بررسی نشست
  -> Next/Vinext App Router
  -> API route داخلی
  -> D1/Drizzle و Cache
  -> سرویس بیرونی مثل Google Sheets، Google Ads، Search Console یا Telegram
  -> پاسخ JSON/CSV
  -> state محلی و کامپوننت‌های dashboard

اجزای اجرایی:

1. Browser UI
   - React Client Components
   - fetchهای brand-scoped
   - localStorage برای برخی صف‌ها و cache آخرین داده
   - PWA Service Worker

2. Vinext/Next App Router
   - صفحه‌ها و API routeها
   - SSR/Client rendering
   - routeهای dynamic برای API

3. Cloudflare Worker
   - نقطه ورود نهایی production
   - محافظت مسیرها
   - image optimization
   - dispatch زمان‌بندی‌شده Telegram
   - forwarding به Vinext handler

4. Cloudflare D1
   - داده‌های برند
   - cache گزارش‌ها
   - تنظیمات مالی
   - sessionها
   - تنظیمات Telegram
   - rule versionها و eventهای سلامت

5. Cloudflare R2
   - logoها و assetهای قابل حذف/ذخیره
   - با binding منطقی BUCKET

6. Cloudflare Images
   - image optimization از مسیر /_vinext/image
   - binding منطقی IMAGES در Worker runtime

11. Telegram Bot و ارسال گزارش
======================================================================

معماری:

داشبورد = مغز گزارش و محاسبات
Google Apps Script یا Cloudflare scheduled trigger = زمان‌بندی
Telegram Bot API = ارسال پیام

route اصلی:

/api/telegram-bot

عملیات:

- GET: خواندن metadata امن تنظیمات و کاربران
- PUT: ذخیره token، تنظیمات و فعال‌سازی
- POST: دریافت update، شناسایی user، گزارش دستی یا scheduler dispatch

امنیت scheduler:

- scheduler بدون session معمولی کار می‌کند.
- header اختصاصی x-telegram-scheduler-secret یا Authorization بررسی می‌شود.
- secret در D1 به‌صورت رمز‌شده نگه‌داری می‌شود.
- کاربر Telegram تا زمان approve دسترسی گزارش ندارد.

منطق گزارش:

- فقط برندهای opt-in وارد گزارش می‌شوند.
- کانال‌های صفر نمایش داده نمی‌شوند.
- مجموع لید/خط هر دفتر برجسته می‌شود.
- delta نسبت به گزارش قبل نشان داده می‌شود.
- هشدار تأخیر داده و خطای source وجود دارد.
- گزارش پایان روز و گزارش زمان عادی تنظیم‌پذیر هستند.
- قفل D1 از اجرای موازی و ارسال دوباره جلوگیری می‌کند.

Cloudflare Worker scheduled:

worker/index.ts در scheduled()، dispatchTelegramReports() را با waitUntil اجرا
می‌کند. ماژول گزارش تنظیمات ساعت، روز و interval را دوباره کنترل می‌کند.

19. روش استقرار روی Cloudflare/Sites
======================================================================

چرخه انتشار استاندارد:

1. وضعیت workspace را بررسی کنید:
   git status --short

2. PROJECT_RULES.md و فایل‌های مرتبط را بررسی کنید.

3. تغییر scoped را با apply_patch انجام دهید.

4. تست‌های مرتبط و سپس build/lint را اجرا کنید.

5. تغییر را commit کنید:
   git add <files>
   git commit -m "<message>"

6. full SHA را بگیرید:
   git rev-parse --verify HEAD

7. از Sites برای source repository یک write credential کوتاه‌عمر بگیرید.
   توکن نباید در فایل، log یا گزارش ذخیره شود.

8. commit دقیق را به branch main push کنید:
   git -c http.extraHeader="Authorization: Bearer <SHORT_LIVED_TOKEN>" push origin HEAD:main

9. build خروجی را package کنید:
   /root/.codex/plugins/cache/openai-curated-remote/sites/0.1.65/skills/sites-hosting/scripts/package-site.sh <PROJECT_DIR> <ARCHIVE_PATH>

10. archive را validate و با tar -tzf بررسی کنید.

11. با Sites save version، project_id، archive و full commit SHA را ثبت کنید.

12. با Sites deploy version، فقط version_id ذخیره‌شده را deploy کنید.

13. status باید succeeded شود و URL production بررسی شود.

14. پس از انتشار git status و version source را دوباره بررسی کنید.

قواعد حیاتی:

- commit_sha باید دقیقاً همان HEAD pushشده باشد.
- archive باید از همان source state ساخته شده باشد.
- version ذخیره‌نشده deploy نمی‌شود.
- project_id و version_id نباید دستی حدس زده شوند.
- برای سایت public از deploy عمومی استفاده می‌شود؛ audience موجود حفظ می‌شود.
- credentialهای push نباید در command history یا فایل persist شوند.
